# СтройCRM

Небольшая CRM для строительной компании: руководитель ставит задачи по стройкам, исполнители берут их в работу и отдают на проверку.  
Сделано по заметкам ТЗ (роли, объекты, статусы, история, экраны, безопасность на уровне базы).

**Стек:** React + TypeScript + Vite, облачный Supabase (вход, Postgres, правила доступа), интерфейс — Mantine, карта адреса — Leaflet.

---

## Что сделано по ТЗ

| Блок ТЗ | Как закрыто |
|--------|-------------|
| Две роли: постановщик и исполнитель | Роли в справочнике `roles`, у пользователя — в `profiles`. Постановщиков и исполнителей может быть несколько. |
| Объект = стройка (название, адрес) | Таблица `construction_objects`, карточка объекта со списком задач и статусами. |
| Задача: название, описание, объект, исполнитель, статус, автор, дата | Таблица `tasks` + карточка задачи. |
| Цикл статусов и запрет чужих переходов | Только через функцию `change_task_status`; прямой UPDATE статуса блокируется. |
| История смен статуса | Пишется автоматически; через API нельзя подделать, править или удалить. |
| Экраны: вход, объекты, карточки, «Мои задачи» | Все экраны есть; кнопки зависят от роли и текущего статуса. |
| Права в базе (RLS), а не только в UI | Политики на таблицах; исполнитель не видит чужие задачи даже при прямом запросе. |
| Без открытой регистрации | Sign ups выключены в Supabase; пользователи создаются вручную. |
| Секреты не во фронте | В приложении только публичный (`anon`) ключ. |

## Финальная архитектура

Система из двух частей: **сайт (фронтенд)** и **облачная база Supabase**. Браузер не «обходит» правила — все запросы идут в Supabase с токеном вошедшего пользователя, а база сама решает, что можно.

```
Браузер (React)
    │  вход по email/паролю, чтение и запись данных
    ▼
Supabase Auth          — кто вошёл
Postgres + RLS         — что этому человеку можно видеть и менять
  ├── profiles         — ФИО, роль
  ├── roles / permissions / role_permissions — права ролей
  ├── construction_objects — стройки
  ├── tasks            — задачи
  └── task_status_history — журнал статусов (только чтение с клиента)
         ▲
         └── смена статуса только через change_task_status()
```

### Как устроены роли

Права не зашиты «магическими if» только во фронте. Есть таблицы ролей и прав: постановщик управляет объектами/задачами и принимает работу, исполнитель только выполняет свои задачи. Проверки в политиках RLS и в функции смены статуса идут через `has_permission(...)`.

### Жизненный цикл задачи

`Новая` → `В работе` → `На проверке` → `Принята`  
             ↘ `На доработке` → `В работе`

- Исполнитель: новая/доработка → в работу → на проверку.  
- Постановщик: на проверке → принята, либо на доработку **с обязательным комментарием**.  
- Остальные переходы база отклоняет.

### Фронтенд (кратко)

| Путь | Назначение |
|------|------------|
| `/login` | Вход |
| `/` | Список объектов |
| `/objects/:id` | Карточка стройки и её задачи |
| `/tasks/:id` | Карточка задачи, действия, история |
| `/my-tasks` | «Мои задачи» (для исполнителя) |

```
src/
  pages/          — экраны
  components/     — оболочка, защита маршрутов, бейдж статуса, карта адреса
  contexts/       — текущий пользователь и профиль
  lib/supabase.ts — клиент с anon-ключом
supabase/
  schema.sql                 — схема, RLS, RPC, триггеры
  auth_profile_triggers.sql  — при создании пользователя в Auth появляется profiles
```

### Безопасность (важное)

- Исполнитель читает только свои задачи и объекты, где у него есть задачи.  
- Статус задачи меняется только через `change_task_status` (роль + допустимый переход + комментарий при доработке).  
- История: клиенту разрешён SELECT; запись идёт из доверенных функций; UPDATE/DELETE запрещены.  
- Открытой регистрации нет. `service_role` не кладётся во фронтенд и в git.

## Быстрый старт

### 1. Supabase

1. Создайте проект на [supabase.com](https://supabase.com).  
2. **SQL Editor** → выполните [`supabase/schema.sql`](supabase/schema.sql), затем [`supabase/auth_profile_triggers.sql`](supabase/auth_profile_triggers.sql).  
3. **Authentication → Providers → Email**: отключите публичную регистрацию (*Enable sign ups* = off).  
4. **Authentication → Users → Add user** — email, password, **Auto Confirm**. Профиль создаст триггер.  
5. Задайте ФИО и роль постановщика:

```sql
update public.profiles
set full_name = 'Иван Постановщик',
    role_id = (select id from public.roles where code = 'manager')
where email = 'manager@crm.local';
```

6. **Project Settings → API**: скопируйте Project URL и `anon` / publishable key.

> Ключ `service_role` во фронтенд и в репозиторий не класть.

### 2. Фронтенд

```bash
cp .env.example .env
# VITE_SUPABASE_URL и VITE_SUPABASE_ANON_KEY

npm install
npm run dev
```

Откройте http://localhost:5173 и войдите тестовым пользователем.

## Проверка вручную

1. Постановщик создаёт объект и задачу на исполнителя.  
2. Исполнитель в «Мои задачи» берёт в работу → отправляет на проверку.  
3. Постановщик принимает или возвращает с комментарием.  
4. В карточке задачи видна история.  
5. Под исполнителем чужие задачи через API/SQL с его сессией не читаются (RLS).
